# Space Autonomy Lab benchmark guide

This guide defines the public benchmark surface and its relationship to the completed scientific
programme. It exists to keep engineering examples, frozen experiments, and higher-fidelity research
results separate.

## 1. Public deterministic harness

Use this layer to exercise a controller against declared faults and explicit acceptance criteria.
It is designed for repeatability, inspection, and integration testing.

```bash
uv sync --frozen --extra dev

uv run python -m kri_space_autonomy.demo build --open

uv run python -m kri_space_autonomy.controller_adapter \
  validate kri_space_autonomy.examples.proportional_controller:controller

uv run python -m kri_space_autonomy.fault_suite \
  run-suite kri_space_autonomy.examples.proportional_controller:controller \
  fault-suites/example-rpo.json
```

The harness produces stable machine-readable and human-readable evidence. A harness `PASS` means
only that the declared example criteria passed in this testbed.

## 2. Core benchmark CLI

The original benchmark API remains available for built-in controller fixtures and checked-in
scenarios:

```bash
kri-space-lab benchmark scenarios/*.json --output results/baseline.json
```

Per controller, the summary records episode count, success count/rate, collision count/rate,
interventions, and unsafe-state steps. Individual episode records remain available in the output.

One scenario can also be run with a hash-chained evidence log:

```bash
kri-space-lab run scenarios/sensor-dropout.json \
  --controller protected \
  --evidence results/sensor-dropout.jsonl

kri-space-lab verify-evidence results/sensor-dropout.jsonl
```

## 3. Frozen confirmatory evidence

The completed research programme uses prospectively frozen designs and separate result packages.
These are scientific records, not examples generated by the public demo.

| Study | Dynamics / measurement boundary | Confirmatory result |
| --- | --- | --- |
| Experiment 002 | Direct-measurement simplified 1-D benchmark | **Favorable** under frozen gates |
| Experiment 003 | Estimator-in-loop simplified 1-D benchmark | **Inconclusive** |
| Experiment 004 | Planar HCW dynamics with independent physical endpoint | **Valid, reproducible, inconclusive** |
| Experiment 005 | Nonlinear central-gravity physical truth with model mismatch | **Valid, reproducible, inconclusive** |

Experiment 004 completed 1,452 paired blocks and 2,904 episodes in its valid replacement campaign.
Its 1,068 primary paired roots had zero physical adverse events in both compared configurations, so
H1 did not establish superiority and H2 was not tested.

Experiment 005 completed 1,068 paired blocks and 2,136 episodes. Fixed-cell validity passed and its
prespecified replay was byte-identical. Again, both configurations had zero physical adverse events
in the frozen primary population, giving zero discordant pairs, risk difference 0, and one-sided
exact p = 1.0. H2 was not formally tested after H1 closed the gate.

These saturated endpoints are valid inconclusive results. They are not repaired, extended, retuned,
or combined into a favorable claim.

## Evidence boundaries

The public demo embeds Experiments 002 and 003 because they share the one-dimensional product-harness
boundary. Experiments 004 and 005 use different dynamical models and physical-evaluation boundaries,
so their results are linked separately.

Do not pool the four studies into a single effect estimate. They answer related but distinct
questions under different measurement and dynamics assumptions.

## Reproducibility and integrity

The repository uses frozen configuration and seed contracts, write-once result paths for scientific
campaigns, deterministic replay subsets, explicit invalid-attempt records, and cryptographic hashes
for evidence identity.

The public benchmark and demo are intentionally cheaper to run than the scientific campaigns. They
are for integration and inspection, not for regenerating historical confirmatory evidence.

## Recommended external workflow

For a new controller:

1. validate the controller adapter contract;
2. run the deterministic fault suite;
3. produce an assurance report under an explicit policy;
4. inspect the public demo bundle;
5. compare behaviour with the frozen research evidence only within matching evidence boundaries.

## Scope

Space Autonomy Lab is research software. The completed programme does not establish flight safety,
operational fault prevalence, 6-DoF validity, hardware-in-the-loop validity, certification, or
KRI-STD-001 conformance.
